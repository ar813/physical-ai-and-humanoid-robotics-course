```text
Add more rule but no replace the existed rules Writing Rules (For the Book Content)

Every lesson must start with a simple explanation before advanced concepts.

Use short sentences and easy vocabulary.

Always give real-world examples (ROS2, Isaac, Gazebo, Humanoid Robots).

Each chapter must include:

Overview

Concepts explained

Code examples

Simulation steps

Practice tasks

Keep paragraphs small (3–5 lines max).

Always add flow diagrams or steps when explaining systems like ROS2 nodes or Gazebo physics.

Summarize each module at the end with key points.

Every chapter should have “Common Mistakes” and “Troubleshooting” sections.

Use images or ASCII diagrams if diagrams help understanding.

Avoid technical jargon unless necessary; if used, define it clearly.

Project Structure Rules (For speckit-plus + docursorus + TypeScript)

Every chapter must be converted into a spec file using spec-kit-plus format.

Use docursorus for generating structured docs, tables, and lessons.

One chapter = one folder in /course/.

One Lab/Module = one spec file (.spec.ts).

Keep specs modular; don’t put everything into one giant file.

Use id, title, objective, and steps clearly in spec files.

Follow the same pattern for every module (ROS → Gazebo → Isaac → VLA).

All code examples must be runnable and tested.

Every example must include TypeScript + Python equivalents only when needed (ROS2/Isaac).

AI Assistant Rules (Claude Code CLI)

All AI-generated code must be simple, clear, and follow TypeScript rules.

Never ask AI to generate huge files; always ask in small chunks.

Tag all generated code with a comment:
// generated by Claude (prompt: <id>)

Always review AI output manually before accepting.

If AI adds unnecessary complexity, simplify it.

All prompts must clearly say what format you want (.ts, .md, .spec.ts, .json).

Use step-by-step prompting:

First outline

Then structure

Then content

Then examples

Don’t let AI guess hardware details — always give specs.

Never allow AI to generate unsafe robot commands without limits.

Code Rules (TypeScript Focused)

TypeScript first — use it for all new logic.

Write types for everything: params, returns, objects, options.

Use interfaces for structured objects.

One file = one feature.

Keep functions small and reusable.

No magic numbers — always use constants.

Use async/await properly; avoid callback hell.

Use ES modules only (import/export).

Put shared helpers in /utils/.

Put reusable types in /types/.

Keep file names clear (rosNode.ts, gazeboSetup.ts, isaacPerception.ts).

Use JSDoc comments for all functions (/** ... */).

Course Workflow Rules

Every module must include a small project or mini-lab.

Use one difficulty style:

Beginner → ROS basics

Intermediate → Gazebo + Isaac

Advanced → Humanoid control + VLA

All labs must provide setup commands (npm run) or ROS launch files.

Use numbered steps (1,2,3…) for all instructions.

Always include hardware alternatives (low-cost → premium).

Same format for every chapter:

Intro

Why it matters

Tools

Code

Simulation

Learnings

All examples must match real-world robotics behavior.

Keep digital twin concepts consistent across modules.

All images used must be stored properly or generated by docursorus.

Safety & Robotics Rules

Always mention safety when dealing with robots.

Real robot code must include speed limits.

Emergency stop must always be included.

Students must run real robot code under supervision.

Explain dangerous scenarios (e.g., unstable biped walking).

Highlight the difference between simulated and physical risks.

Final Project (Capstone) Rules

Capstone must follow a strict structure:

Voice → Plan → Navigate → Detect → Manipulate

All subsystems must be modular and testable separately.

Capstone must run in simulation first before real hardware.

Students must document latency, safety, and sensor calibration.

Final report must include architecture diagram + flowchart.
```
